Main findings:

1. **The Master Anchor works differently from the doc.** The code publishes a *deny list* (`revoked_keys`), not an *allow list* (`temporary_keys`). The receiving node reads it to check the caller's key at connection time. Clients do not list a master's active devices. Temporary and instance keys never publish their own DHT record. A substrate's record is signed by its own long-lived node key. Member records are signed by the member's master key. The anchor is also only valid for 24 hours, so a master must refresh it (the supervisor does this every 12 hours).
2. **The router does not check that the caller holds the temporary key.** `HandshakeVerifier::verify_preamble` checks the certificate chain and the revocation list, but the key in the preamble is only asserted. Nothing asks the caller to sign a challenge. The SDK code says so itself. Only the auth service login checks a signature over a nonce. The doc lists "Did the Temporary Key sign the active request?" as step 1. This is a real gap in the code and in the doc. See Q2.
3. **Nearly all of Trust & Reputation, Discovery placement/ranking, and Payments is not built, and none of it is marked Envisioned.** There is no vouching, no `ReputationRecord`, no ranking formula, no ad boost, no `PaymentIntent`, no payment adapter, no mutual credit and no coin. Roym has a directory service (client fan-out to chosen directories, newest first, client-side verification) and signed payment *records* that never move money.
4. **Messaging names the wrong libraries.** 1:1 chat uses `vodozemac` (X3DH + Double Ratchet style). Group chat uses one AES-256-GCM key per epoch, sent over the 1:1 channel, with a signed gossip DAG. MLS and `openmls` are not used. The Roym spec records this as a decision (it amends ADR-0013).
5. **Tier 1 (government identity) and the ZK plugin do not exist**, and the requirements spec says no government ID is the universal root. The "Master Key Compromise (Tier 1 Fallback)" flow is therefore not built either.

## 4. Gaps noticed

Architecture-relevant code that this part does not mention:

1. **Substrate ownership.** A `ControllerAgreement` and `roymctl substrate claim` decide who owns a node, and ingress grants `substrate/admin` to that root (`crates/identity/src/substrate.rs:48`; `crates/router/src/route_handler/io.rs:158-215`; `crates/substrate/src/identity.rs:19-90`).
2. **Node auth service.** A nonce challenge, a delegated-key or local login, and a short-lived session token (`crates/auth/src/service.rs:243-335`; `crates/auth/src/token.rs`).
3. **Anchor freshness duty.** An anchor stops verifying after 24 hours. A missing or stale anchor makes the handshake fail closed. The supervisor republishes every 12 hours (`crates/core/src/dht_registry/master_anchor.rs:152-165`; `crates/core/src/config/roles.rs:155-162`).
4. **Certificate scopes.** `routing`, `session-auth`, `service-instance`, `record-signing`. `record-signing` is not allowed as a connection identity (`crates/identity/src/delegation.rs:12-30`).
5. **Signed record envelope.** One verifier and a fixed table of record types; the signing key stays behind the `syneroym:signing` WIT boundary (`crates/signed_record/src/lib.rs:1-12`; `crates/roym_core/src/record.rs:18-31`).
6. **UCAN capability model.** A UCAN chain presented in the preamble becomes the caller's capabilities, with a revocation check per chain edge (`crates/ucan/src/token.rs:221`; `crates/router/src/route_handler/io.rs:69-85,218-235`; ADR-0015).
7. **Group chat controls.** Epoch rekeying, signed membership events, first-contact admission and holds, and deletion requests (`crates/conversation/src/group.rs:560-580`; `crates/roym_core/src/safety.rs:87-136`; `crates/conversation/src/dag.rs:26-33`).
8. **SynOrg model.** A directory is run by a group that issues membership credentials, revocations and moderation decisions, and each consumer pins which group a directory speaks for (`crates/roym_core/src/membership.rs`; `crates/roym_directory/src/app/standing.rs`). The Discovery and Trust sections have no place for this.
