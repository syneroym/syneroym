### Main findings

1. **Substrate security, envelope encryption, and memory protection are robustly implemented.** Envelope encryption with per-service SQLCipher DEKs and memory-locked master KEKs is delivered (`crates/data_keystore/src/key_store.rs:29-50`). Per-instance KEK derivation via HKDF-SHA256 scoped by `service_id` (Model A) provides defense-in-depth across service databases, while IAM-gated per-instance KEK provisioning (Model B) remains deferred per ADR-0006. Secrets are secured in dedicated SQLite `_vault` tables and accessed via `syneroym:vault/reveal` host functions. OS-level memory locking (`mlock`) and explicit RAM wiping via `zeroize` protect key memory. Runtime quotas are enforced via Wasmtime fuel metering and memory caps. Hardware attestation (`substrate.attest(nonce)`) is unbuilt.
2. **In-repo deployment scripts cited in the spec do not exist.** The spec claims initial provisioning and deployment are handled by `scripts/deploy/setup_linux.sh`, `scripts/deploy/deploy.sh`, and `.github/workflows/deploy.yml`. None of these files exists in the repository. Actual deployment and release distribution rely on `Dockerfile`, `deploy/docker-compose.community.yml`, `.github/workflows/release.yml` (multi-arch Linux, macOS universal, Windows), and `crates/smoke-tests/src/main.rs`.
3. **FDAE access control and the 4-stage hybrid pipeline are fully delivered.** The Zanzibar-style ReBAC policy compiler, pushdown sieve into SQL `WHERE EXISTS` / `WITH RECURSIVE` queries, Mode A point-in-time checks, Mode B relational filtering, and stage-4 guest-exported ABAC after-steps are operational (`crates/fdae`, `crates/rpc/src/fdae_fetch.rs`, `crates/rpc/src/fdae_abac.rs`). Write-side authorization (`put`, `patch`, `delete`, `batch_mutate`) enforces Postgres-style `USING`/`WITH CHECK` rules in SQLite transactions.
4. **Service configuration delivery and dependency composition match architectural decisions.** WASM services access hierarchical configuration via `syneroym:app-config/get` with immutable generation pinning per invocation (`crates/sandbox_wasm/src/host_capabilities/capabilities_services.rs:231`), while Podman containers receive flattened environment variables and read-only file mounts (`crates/sandbox_podman/src/engine.rs`, ADR-0019). App composition supports deploy-time manifest inlining (`Spawn`) and external dependency binding (`Bind`) with stable member identities surviving restart (ADR-0020).
5. **The Asynchronous Operations section contains direct internal contradictions between its status note and body text.** Line 1032 embeds an implementation status note (M05B, ADR-0023) detailing six required corrections to the narrative text below it. The body text continues to describe an obsolete Registry-backed distributed lease scheduler (lines 1063–1067), snake_case `undo_<operation>` endpoints accepting "generated resource IDs" (lines 1069, 1075), and client-side outboxes (lines 1054, 1056). In code, scheduled tasks use target selection plus local overlap guards on the App Supervisor without Registry leases, saga endpoints are named `saga-undo-<operation>` taking forward parameters plus return values (`crates/app_orchestration/src/saga.rs:14`), and the outbox is substrate-side (`crates/async_queue/src/queue.rs`). Long-running task restart rules are deferred.
6. **Service Redundancy (`[PLT-RED]`) is correctly framed as a P1 hardening track, with distributed replication largely unbuilt.** Single-node SQLite storage, local in-process MQTT broker (`rumqttd`), and S3-compatible blob storage are fully operational. However, multi-node SQLite WAL streaming, broker topic-log replication over QUIC, P2P blob replication across substrates, deposition quarantining (`QUARANTINED`), and routing-level fencing are not built (targeted for M7). Structural isolation of data plane from control plane availability per ADR-0021 is fully implemented.

## 4. Gaps noticed

1. **FDAE Write-Side Integrity Pipeline (`crates/data_db/src/sqlite.rs`, M04B Slice B5).** Access Control lines 971–986 cover FDAE read-side filtering (RLS/CLS pushdown sieve, Mode A, Mode B, Stage-4 ABAC after-step), but completely omit write-side authorization: single-row `put`, `patch`, `delete`, and `batch_mutate` operations are authorized within the same SQLite transaction using Postgres-style `USING`/`WITH CHECK` semantics (ADR-0017 §2.1). Field authors cannot alter CLS-masked attributes or reassign `creator_id`, and `System`-caller writes deny closed under a policy.
2. **`StaticInventory` and Configuration Push for Inter-Service Dependencies (`ADR-0021`, `crates/app_orchestration/src/resolver/registry.rs`).** Lines 962–964 (`[FND-CFG]`) and line 1022 (`[PLT-DAT]`) refer to resolving service imports by consulting an "Orchestrator Registry". The spec omits the built mechanism of ADR-0021: the App Supervisor pushes dependency bindings directly into service configuration at deployment/scaling time, populating `StaticInventory` and completely bypassing runtime registry lookups on the RPC hot path.
3. **Master DID per Service Member vs per Physical Instance (`ADR-0020`, `crates/identity/src/keys.rs`).** `[FND-IDT]` (lines 936–939) describes an issuer-neutral key hierarchy, but omits the stable service identity architecture designed in ADR-0020: each member of a logical service maintains a stable master DID, while physical instances run under rotatable ephemeral keys certified by `DelegationCertificate` scoped by `SCOPE_SERVICE_INSTANCE`, allowing relocation and restart without altering FDAE row attribution or identity continuity.
4. **App-Instance Master DID (`crates/app_supervisor/src/`, M05A Slice A7).** In addition to service-member master DIDs, each running `SynAppInstance` carries an app-instance master DID minted at `adopt`, preserved across supervisor handovers, and exportable/importable via `export-master`/`import-master`.
5. **Receiver-Side Idempotency and Deduplication Fences (`call_dedup`, `crates/router/src/call_dedup.rs`, `crates/async_queue/src/dedup.rs`, ADR-0023).** `[PLT-ASY]` covers outbox queues and retries, but omits the core mechanism guaranteeing exactly-once processing: the substrate maintains sliding-window hash rings and durable deduplication tables (`call_dedup`) that track incoming request IDs and idempotency keys, rejecting replayed requests within the deduplication horizon.
6. **Mismatched Asserter Identity Protection in Federated FDAE (`crates/rpc/src/fdae_fetch.rs`, ADR-0015 / ADR-0017).** In Stage 2 of the 4-stage pipeline, the spec describes fetching parameters across services, but omits the cryptographic trust anchor rule: policy declarations specify `expected_asserter_did`, ensuring remote claims from unverified nodes or relays are rejected fail-closed.
7. **SIGUSR1 Hot-Reload for TLS Certificates without Restarts (`crates/core/src/tls.rs:26-58`).** Line 896 states "The substrate restarts or reloads configuration to pick up renewed certificates." The actual built mechanism uses `TlsCertLoader` which listens for the OS-level `SIGUSR1` signal to reload certificates in-place from disk without terminating the process or interrupting active connections.
8. **Substrate Claim & Controller Agreement Gate (`crates/identity/src/substrate.rs`, `roymctl substrate claim`, Slice P0).** The spec mentions owner control in `[FND-IDT]`, but omits the substrate ownership bootstrap ceremony: an unowned substrate allows initial claiming via `roymctl substrate claim`, creating a mutual-signature `ControllerAgreement` that locks the substrate's admin interface to the owner's master DID.
9. **Dead Letter Queue Inspection Surface in CLI (`roymctl`, `crates/async_queue/src/dlq.rs`).** `[PLT-ASY]` line 1051 mentions routing failed messages to a DLQ, but omits the built operational query/replay capabilities that allow administrators to inspect failed messages and review failure diagnostics.
