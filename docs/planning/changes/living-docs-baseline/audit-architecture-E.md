# Audit: architecture doc, batch E

Reader: a developer who will split and fix [system-architecture.md](../../../system-architecture.md).

Batch E covers two sections of the architecture doc:

- "Appendix: Multi-Hop Relay Walkthrough" (Scenario Entities, steps 1 to 5).
- "Consolidated Technology Stack" (Core Infrastructure & Substrate, SynApp & Crypto Libraries, Consumer Frontend, Developer Toolchain).

Part of the [living docs baseline](change.md). This audit changes no code and does not edit the doc. All checks are static reading. I did not run the substrate or the tests. Format follows [audit-architecture-layer2.md](audit-architecture-layer2.md). Batch A, section 3, was read only to avoid contradicting it. Repeats of its findings are marked "repeat of A".

**How to read the verdicts.** Only code and tests count as proof. Paths are from the repository root. Every MATCHES row has a `file:line` citation.

- **MATCHES**: the code does this.
- **DIVERGES**: the code does something different. The code is right, so the doc needs a fix.
- **NOT BUILT**: nothing in the code does this. "Presented as" says whether the doc writes it as working or as planned.
- **STALE**: the name no longer exists. The current name is given.
- **UNCLEAR**: I could not decide. The row says what I looked at.

**Shorthand.** Entities from the Appendix: C = global coordinator, R = global registry, Cp = private coordinator, Rp = private registry, Sx = public substrate, Sz = hidden substrate, Ax and Az = SynApps on them. `io.rs` = `crates/router/src/route_handler/io.rs`. `multi_hop_relay.rs` = `crates/coordinator_iroh/tests/multi_hop_relay.rs`.

Main findings:

1. **The Appendix describes a coordinator-centered design that is only partly built.** What works (proven by `multi_hop_relay.rs:565-650`): a coordinator that receives a stream for a service it does not host looks the target up in the registry and pipes bytes to it (`io.rs:317`, `io.rs:471-515`). What does not exist: a substrate that finds a coordinator through `discovery_url` or the registry (S1-09, S1-10, S4-04, S4-05), a registry that asks its parent on a lookup miss (S4-03), and a record that names Cp as entry point (S2-06, S3-03). `SyneroymClient::deploy_wasm` does not exist (S2-01).
2. **The end-to-end handshake is one-sided and optional.** The doc says both ephemeral keys are signed (mutual authentication). In code only the server signs (`crates/router/src/route_handler/encryption.rs:312-328`). It runs only when the caller sets `enc=ecdh-p256`. The Rust client never does. (Same root as A's MH-10.)
3. **The technology table has 15 wrong or unbuilt rows.** Examples: Rust edition is 2024 not 2021; `iroh-net` is not a dependency; OpenTelemetry/OTLP, Hickory DNS, `libsignal-protocol-rust`, `openmls`, `ssi`, Shaka, Stripe, `podman-compose`, `otelcol` and the native shell are not in the code; "derived automatically from WIT" is false (the dispatch tables are hand-written). The Litestream note contradicts `[PLT-RED]`.

## 4. Gaps noticed

Architecture-relevant behavior in the code that this batch does not mention (at most 8).

1. **Coordinator registration is one-shot.** `register_coordinator_in_registry` posts once, with retry only on failure (`coordinator.rs:468-509`). A registry entry is dropped after 2 hours without a refresh (`types.rs:16`, `registry.rs:145-157`). Substrates re-register every hour (`HEARTBEAT_INTERVAL_SECS`, `types.rs:20`); coordinators do not. A coordinator's record vanishes from R after 2 hours. Candidate backlog item.
2. **`pubkey` has two meanings in the preamble.** `handshake.rs:25-45` reads it as an Ed25519 key. `encryption.rs:287-298` reads it as a P-256 key. A stream with `enc=ecdh-p256` and a `delegation` certificate would fail the Ed25519 length check and be rejected as unauthorized (`io.rs:411-421`). This is my reading of the code. I did not run it.
3. **The ECDH secret is the AES key.** `encryption.rs:303-307` copies the first 32 bytes of the raw shared secret into AES-256-GCM. There is no key derivation step, and the client key is not signed (S5-05). Worth a design note or an ADR check.
4. **`/v1/info` reports more than the doc says.** Status, active connection count and cap, TLS certificate expiry in days, relay online flag: `crates/coordinator_iroh/src/info_endpoint.rs:23-66`. A coordinator also enforces `max_connections` (`route_handler.rs:461`).
5. **Record visibility is a built model.** `Publication::{Private, Internal, Public}` decides whether a record stays local, stays on one registry, or goes up to the parent registry and the DHT: `crates/sdk/src/types.rs:38-48`, `crates/core/src/dht_registry/client.rs:146-152` (ADR-0018 section 4). The Appendix does not describe it.
6. **The substrate never holds a member's signing key.** Hosted-service records are signed by the deployer and only replayed by the substrate (`endpoint_publisher.rs:1-9`; ADR-0020 section 3). Relevant to step 2.
7. **Toolchain list is narrow.** `mise.toml` also installs `cargo-nextest`, `cargo-audit`, `cargo-deny`, `cargo-dupes`, `cargo-llvm-cov`, `cargo-sweep`, Node 20 and the nightly rustfmt pin. The e2e suite uses Playwright 1.60.0 and TypeScript 5.9.3 (`crates/substrate/tests/e2e/package.json`). The Hub UI uses Vite and Vitest (`crates/roym_web/ui/package.json`). The table lists none of them. `mise run verify` is the real completion gate.
8. **Version drift.** Guest test components pin `wit-bindgen` 0.55.0 while the workspace uses 0.57 (T19). `Cargo.toml:110` has a stale comment on `webrtc` 0.17.
