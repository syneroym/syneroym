# Audit: requirements spec, overlaps, questions and fix order

Reader: a developer who will apply the fixes to [system-requirements-spec.md](../../../system-requirements-spec.md) and [traceability-matrix.md](../../traceability-matrix.md).

This file merges sections 3 to 6 of the requirements specification audit reports. The reports are batches R1 through R9 and the gap report ([audit-requirements-GAP.md](audit-requirements-GAP.md)). It is part of the [living docs baseline](change.md). I changed no code and no doc. I did not re-audit the code. Where a report did not say which copy the code supports, I read the code to decide. In every other row I used the report's verdict.

How to use it:

- Part 1 lists every statement that the spec or matrix writes in more than one place, or writes in two different ways. Each row names the copies by heading and first words, what the code supports, and the action.
- Part 2 lists every question with its default. A star marks a question that needs a stakeholder decision before you edit.
- Part 3 lists every place that cites a milestone ID, a commit hash or a dated note.
- Part 4 gives the proposed order of the fix commits.
- Part 5 gives the merged, ranked requirements gaps.
- Part 6 summarizes the audit findings and batch statistics.

Notes that apply to everything:

- All checks compare documentation against static code, tests, and configuration.
- Where one statement appears in multiple sections, fix all occurrences in a coordinated pass.
- "Req spec" refers to `docs/system-requirements-spec.md`. "Traceability matrix" refers to `docs/planning/traceability-matrix.md`. "Roym spec" refers to `docs/roym-integrated-experience-spec.md`.
- Report IDs: `R1-D3` is batch R1 duplicate 3; `R5-Q2` is batch R5 question 2; `GAP-14` is row 14 of the gap report.

### 6.2 Key Takeaways

1. **Substantial Working Foundation (291 Implemented, 50.1%):** Half of all audited items are fully implemented in code and backed by passing integration and unit test suites. This includes the core Iroh QUIC networking, router and preamble dispatch, App Supervisor orchestration, Wasmtime component isolation, data layer SQLite management, Roym application services, bilateral agreement receipts, and encrypted identity backups.
2. **Substantial Partially-Built Features (125 Partial, 21.5%):** Many requirements describe architectures that are partially functional today but missing planned extensions: same-version identity restore works while cross-version fixtures are deferred; DDL migration hooks execute while automated snapshot rollback is unbuilt; in-memory metrics record histograms while persistent rollups do not exist; directory fanout operates while leaf index shards are unbuilt.
3. **Deferred and Envisioned Capabilities (80 Not Built, 13.8%):** Features described in later roadmap phases — decentralized escrow, hardware attestation, local AI concierges, mobile phone substrates, BLE/LoRa mesh transports, and multi-sig voting — have no code presence and must be cleanly marked as Envisioned.
4. **Architectural Divergences (23 Diverges, 4.0%):** A critical set of divergence patterns exists where built code intentionally chose an alternative architecture: bilateral independent receipts replace joint DHT reputation records; out-of-band payment records replace Stripe SDK integration; Roym booking tracks replace the draft/paid/dispute order state machine; Master Anchor implements a revocation deny list rather than an allow list.
5. **Stale Concepts and Terms (13 Stale, 2.2%):** Obsolete terminology (`SYN-MOD`, `Space`, `Space Manager`, `Bootstrap Server`, `setup_linux.sh`) persists in the specification and must be replaced with accurate system terms.
6. **24 Unrepresented Capabilities Added (GAP Report):** Core production systems — including the Client Gateway, Node Ownership Claiming, Host-Only Signing Boundary, Dual-Build Execution, and Control-Plane Alert Engine — were operating without explicit system requirements. Inserting these 24 requirements completes the system specification baseline.
