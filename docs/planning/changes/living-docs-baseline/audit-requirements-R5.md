### Main findings

1. **The reference vertical contract is solidly implemented as Roym, but the second reference vertical is unbuilt.** The Home Services Guild workflow is implemented end-to-end by the Roym application (`crates/roym_core/app/roym.toml`, `crates/roym_catalog`, `crates/roym_directory`, `crates/roym_profile`, `crates/roym_transaction`, `crates/roym_conversation`, `crates/roym_web`). The second reference vertical mentioned in the introduction and executive summary ("Food & Small Retailer Mesh" / retail spaces) is not built (Owner Decision Q-A2; Overlaps O21).
2. **The consumer-provider transaction workflow matches the code, with referral links and consumer feedback Envisioned.** The Discover, Assess, Request, Quote, Fulfil, Settle, and Close phases are implemented via strongly-typed signed record payloads (`RequestPayload`, `AgreedTerms`, `AgreementRecord`, `BookingState`, `BookingProgressPayload`, `FulfilmentRecord`, `InteractionReceipt` in `crates/roym_core/src/transaction.rs:86-150` and `booking.rs:38-62`). Out-of-band payment acknowledgement is built. Referral links and consumer feedback/reviews tied to receipts are unbuilt (Owner Decision Q-B3; Matrix row 14 `[PRD-TRU]` / `[P2P-REP]` open for M8).
3. **The seven Service Variation Dimensions directly mirror the seven optional blocks of the listing schema.** In `crates/roym_core/src/listing.rs`, `ListingPayload` implements the variation axes as explicit structs: `BookingTerms` (slots/order/enquiry), `PaymentTerms` (fixed/per-hour/per-unit/quote-only), `ProductDetail` (condition/unit/pack/sku), `ServiceDetail` (duration/includes/excludes), `LocationTerms` (provider/customer/remote/area), `RelationshipTerms` (open_to/member_of), and `ServiceRecordTerms` (warranty/retention). Single quote payments are built; multi-part payments, subscriptions, escrow, system coins, and mutual credit are explicitly deferred.
4. **Core primitives and the control plane overlay are fully implemented, including app-instance namespaces and composability.** `SynSvc` acts as the zero-trust execution boundary (`crates/sandbox_wasm`, `crates/sandbox_podman`, `crates/control_plane/src/synsvc_native.rs`) with per-service databases and FDAE ReBAC policy enforcement (`crates/fdae`). `SynAppManifest` serves as the deployment blueprint and lifecycle boundary (`crates/app_orchestration/src/models/manifest.rs`). Deploying manifests creates isolated `SynAppInstance` namespaces (`crates/app_orchestration/src/models/instance.rs`). App composability is implemented via `AppDependencySpec::Spawn` (recursive compilation) and `AppDependencySpec::Bind` with cycle detection (`crates/app_orchestration/src/compiler.rs:149-177`).
5. **The contextual registry and discovery mechanisms diverge from the spec per ADR-0021.** In line 846, the spec acknowledges ADR-0021 ("binding propagation by push; no live app directory"). However, lines 853–858 still describe a runtime queryable `syneroym-core/registry` SynSvc with `Spawn` and `Bind` modes. In code, runtime queryable app registry services were discarded in favor of configuration push into `StaticInventory` (`crates/app_orchestration/src/resolver/registry.rs:48`, `crates/app_supervisor/src/inventory.rs`). In addition, the Master Anchor DHT record structure in code is a cryptographic **revocation deny list** (`revoked_keys: Vec<String>` in `crates/core/src/dht_registry/master_anchor.rs`), not an array of authorized temporary keys.
6. **Network robustness and reactive connection management are operational.** Automatic connection retries with exponential backoff and jitter are implemented in `crates/core/src/retry.rs` and `crates/router/src/net_iroh.rs`. Standard QUIC idle timeouts are configured without custom application-level ping/pong heartbeats. Stale connections are evicted reactively upon read/write failure. Non-idempotent queued calls without idempotency keys are refused per ADR-0023.

## 4. Gaps noticed

1. **Listing Seven Optional Named Blocks Architecture (`crates/roym_core/src/listing.rs:50-175`).** Service Variation Dimensions (lines 751–772) lists seven variation axes as narrative prose, but omits the actual built schema: `ListingPayload` implements precisely these 7 dimensions as strongly-typed, optional named blocks (`BookingTerms`, `PaymentTerms`, `ProductDetail`, `ServiceDetail`, `LocationTerms`, `RelationshipTerms`, `ServiceRecordTerms`) with bound integers, explicit currencies, micro-degree areas, and reproducible canonical content digests.
2. **Address Disclosure Protocol via Data Flag (`AddressDisclosure::OnAgreement`, `crates/roym_core/src/listing.rs:132-137`, `crates/roym_core/src/transaction.rs:98-110`).** Line 734 states "Exact address is disclosed only when needed," but omits the built cryptographic and schema mechanism: `LocationTerms.address_disclosure` carries the disclosure policy as machine-readable data (`OnAgreement` vs `Public`), withholding the provider's exact address from public listings and requests until quote acceptance in an `agreement-receipt`.
3. **Double Ratchet E2EE for Multi-Tenant Operator Isolation (`crates/conversation/src/crypto.rs:233`, `ADR-0013`).** Line 722 states that an operator manages multiple providers without obtaining undeclared read access across private conversations, but omits the concrete built encryption mechanism: 1:1 conversations use `vodozemac` Double Ratchet end-to-end encryption with ephemeral X3DH key agreements, ensuring the substrate operator cannot read conversation plaintext.
4. **Binding Propagation by Push & `StaticInventory` (`ADR-0021`, `crates/app_orchestration/src/resolver/registry.rs:48`, `crates/app_supervisor/src/inventory.rs`).** Line 846 mentions ADR-0021 in passing, but lines 853–858 describe spawning dedicated or shared runtime queryable registry SynSvcs. The spec omits the full built architecture: the App Supervisor pushes dependency bindings into each service's configuration at deploy/scale time, eliminating the runtime queryable registry on the hot path while maintaining local rendezvous hashing and sharded selection.
5. **Two-Tier Logical Service Discovery (`ADR-0022`, `crates/app_orchestration/src/models/service.rs:250-262`).** Service Addressing and Resolution Topology (lines 820–840) defines addressing types, but omits the built two-tier discovery model: intra-app dependencies use push via ADR-0021, while inter-app/cross-installation consumers query signed, cacheable topology documents (`TopologyVisibility::Open` vs `Restricted`), avoiding both global indexes and unauthenticated disclosure.
6. **Master Anchor as Revocation Deny List (`crates/core/src/dht_registry/master_anchor.rs`, `ADR-0020`).** Line 861 states that the Master Key maintains an array of currently authorized temporary keys in DHT. The spec omits the actual built pattern: temporary keys carry signed `DelegationCertificate` credentials, and the Master Anchor pkarr DHT record publishes a signed `revoked_keys: Vec<String>` deny list that invalidates compromised keys on connection failure.
7. **Deterministic Round-Robin Client Merge Engine (`crates/roym_directory/src/app/client_merge.rs:16-47`, `client_query.rs`).** Line 728 mentions searching one or more guild directories, but omits the built client merge engine: concurrent fan-out across multiple directory DIDs, deduplication by listing ID, attribution with source DID and recency, and interleaving bounded by `MAX_HITS_PER_SOURCE` (10) and `MAX_SEARCH_RESULTS` (50).
8. **App Dependency Graph Compilation with `Spawn` and `Bind` (`crates/app_orchestration/src/compiler.rs:149-177`).** Composable SynApps (lines 813–817) discusses app composition conceptually, but omits the built compilation engine: `SynAppManifest.dependencies` supporting `AppDependencySpec::Spawn` (recursively compiling child instances with inherited placements) and `AppDependencySpec::Bind` (binding to existing instance namespaces with cycle detection).
