# Audit: architecture doc, Addendum intro and Phases 0-2 (batch G1)

Reader: a developer who will split and fix [system-architecture.md](../../../system-architecture.md).

This audit checks one part of the architecture doc against the code. The part is
the heading "Post-DD864A1 Target Designs (Addendum)" with its intro, then
"Phase 0: Core Architecture Implementation" (`[TOP-PRM]`, `[TOP-ADR]`,
`[TOP-REG]`, `[TOP-DSC]`, `[TOP-ROB]`), "Phase 1: Foundation & Core
Infrastructure" (`[FND-SEC]`, `[FND-CFG]`, `[FND-IAM]`) and "Phase 2: Core
Platform Capabilities" (`[PLT-DAT]` with its five numbered parts, `[PLT-ASY]`,
`[PLT-RED]`). It is the doc text at lines 1841-2158 at the time of the audit.
It changes no code and does not edit the doc. Part of the
[living docs baseline](change.md).

**How to read the verdicts.** Only code and tests count as proof. Paths are from
the repository root. Every MATCHES row has a `file:line` citation. The verdicts
describe what the audit found. They are not doc status values.

- **MATCHES**: the code does this.
- **DIVERGES**: the code does something different. The code is right, so the doc needs a fix.
- **NOT BUILT**: nothing in the code does this. "Presented as" says whether the doc writes it as working or as planned.
- **STALE**: the name, number or note no longer matches. The current name is given.
- **UNCLEAR**: I could not decide. The row says what I looked at.

All checks are static reading. I did not run the substrate or the tests.
The Layer 2 pilot report is [audit-architecture-layer2.md](audit-architecture-layer2.md).
The Layer 2 section of the doc has since been rewritten and marked (commits
"fix and mark layer 2" and "mark redundancy options as open"). So where this
batch repeats a Layer 2 claim, I cite the `L2-xx` row of the pilot.

**The addendum is marked almost nowhere.** The doc's status legend (lines 3-4)
says no marker means implemented, and anything not built must carry
**Envisioned**. This part has no Envisioned marker. Most unbuilt items
here are written as working design ("The Shipper (Primary): A background Rust
task receives..."). Each NOT BUILT row below says "Presented as".

Of the 38 NOT BUILT claims, 25 are presented as working and 13 as planned (see "Presented as" in each row).

Main findings:

1. **The Phase 2 data-plane designs for query and replication are not built.** DataFusion, Substrait, Arrow streams (`syneroym:data/stream`, `syneroym:data/transform`), WAL shipping, `wal-backup`, node states (`QUARANTINED`), fencing, denylist and peer blob replication have no code. All of them are written as working design. Eighteen of the NOT BUILT rows are in `[PLT-DAT]` parts 4-5 (G1-130 to G1-136) and `[PLT-RED]` (G1-153 to G1-163).
2. **Several "target design" statements are already wrong in the other direction.** The code is ahead of the text: aggregation is built (`$group`, `$having`, ...), the dead-letter queue exists, the master anchor record is signed and resolved, the native-dispatch caller gate is mandatory, and the app supervisor exists. The doc still says "deferred", "does not exist" or "no delegation required".
3. **Key mechanism differences, all in code that works.** The rendezvous hash input has an extra `service_name` field. Entity-tag sharding splits the key at the first zero byte. The deployment journal has `DEGRADED` and no `ROLLBACK_FAILED`. Per-service SQLite files set no WAL mode. The FDAE cross-service fetch is a plan, fetch, finalize sequence and not a "halt SQL and call a host extension". The collection schema is only a list of indexes, so "unknown fields rejected" is false.
