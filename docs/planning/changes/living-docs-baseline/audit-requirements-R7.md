### Main findings

1. **Application lifecycle management (`[LFC-MGT]`) matches the built architecture across both operational modes.** The declarative manifest format (`SynAppManifest`), explicit dependencies (`requires`), static binding injection, substrate inventory (`substrates.toml`), and UCAN deploy admission are operational (`crates/app_orchestration`, `crates/app_supervisor`). Both the one-shot standalone CLI (`roymctl app deploy`/`reconcile` with SQLite journal `deployments.db`) and the active control plane (`AppSupervisor` with continuous reconciliation, health monitoring, bounded remediation, and alerting per ADR-0021) are fully implemented.
2. **Version rollback mechanisms (`[LFC-VER]`) diverge between metadata and state.** At deploy time, the control plane rolls back config generations, static asset bundles, and FDAE policies when an installation fails (`crates/control_plane/src/service/orchestration/backends.rs:151-244`). However, automatic filesystem-level SQLite database snapshots before upgrades, automatic schema migration rollbacks, and substrate binary rollbacks via `roymctl revert` (a non-existent command) are not built. Handshake protocol version negotiation is deferred alongside wRPC per ADR-0014 / M04A Decision Register A.7.
3. **Observability enhancements (`[ADV-OBS]`) are in-memory only; data rollups and access control are unbuilt.** The substrate records in-memory counters, gauges, and histograms via the `metrics` facade (`crates/observability/src/recorder.rs:25-30`) and serves a JSON snapshot via HTTP `GET /metrics` (`crates/substrate/src/runtime/services.rs:390-410`). Dedicated SQLite storage (`metrics.db`), automatic 24-hour raw to 1-hour bucket rollups, per-stream network byte counters (`bytes_tx`/`bytes_rx`), GPU/LLM token metering, and role-based metrics access control (substrate owner vs service owner vs relay provider) do not exist.
4. **All Advanced AI & Agentic Workflows (`[ADV-AI]`) are completely unbuilt.** There is zero code, configuration, or dependency in the repository for Ollama, managed local inference, rig-core concierge agents, dynamic tool retrieval loops, Proposal Cards for human-in-the-loop consent, agent progress streaming, Model Context Protocol (MCP) gateways, autonomous agent negotiation, `sqlite-vec` vector stores, or nested Loopcraft loops. In the reference product specification (`docs/roym-integrated-experience-spec.md`), AI assistants are explicitly scoped out of the initial release. All `[ADV-AI]` claims are Envisioned.
5. **Developer tooling (`[ADV-DEV]`) relies on standard Cargo and dual-build linking; claimed templates and mock SDKs do not exist.** Development uses standard Rust tooling (`cargo-component`, `wasm32-wasip2`) and integration tests run against real local substrate nodes (`syneroym-substrate`, `SubstrateTestContext`). However, `cargo generate` project templates, the `roymctl dev` CLI subcommand, and the in-memory mock SDK (`syneroym-dev-sdk`) do not exist in the repository. Furthermore, while the spec describes SynApps as coupled purely through WIT interfaces without compile-time bindings, Roym services also support compile-time native linking via `syneroym-app-host-native` (`crates/app_host_native`, matrix row 55).
6. **Peer-to-peer community primitives (`[P2P-DSC]`, `[P2P-REP]`) are deferred to M8, while Roym implements SynOrg-based directories and signed trust evidence.** Distributed matching fabric with rendezvous-hashed leaf index shards is not built (matrix row 56: "The Guild Directory is deliberately not `[P2P-DSC]` (M8)"). Similarly, coarse-grained satisfaction signals (0/1/2 integer scores), time-decay formulas, and substrate rolling summaries are unbuilt. Instead, Roym implements directory search over client-selected SynOrg sources (`crates/roym_directory`) and trust verification based on portable signed records (membership credentials, revocations, and interaction receipts) without public scores (`crates/roym_core`, `roym_trust_e2e.rs`).
7. **The Syneroym Hub and consumer/provider apps are delivered as a web client over gateway JSON-RPC, not a native shell.** Shipped in M06C, the Hub (`crates/roym_web/ui`) is a thin browser application (Vite + TypeScript) communicating with substrate services over HTTP JSON-RPC (`POST /rpc`) with bearer session tokens. It renders versioned Action Cards from fixed templates (`crates/roym_core/src/card.rs`), supports social and group chat (`crates/roym_conversation`, `crates/conversation`), quote/invoice negotiation (`crates/roym_transaction`), directory publishing, and trust inspection. Map-based mesh radars, multi-service bundling, automated debt clearing, and fiat gateways are unbuilt.
8. **Mobile edge operations (`[EDG-MOB]`) are Envisioned.** Responsive web access is operational in the browser, and substrate outbox retry semantics exist (`crates/async_queue`). However, native mobile substrate execution on Android/iOS, silent APN/FCM push wake-ups, deferred network response windows, and hardware security WIT abstractions (`SecureStorage`, `KeyManagement` mapping to StrongBox, Secure Enclave, or TPM 2.0) are completely unbuilt.

## 4. Gaps noticed

1. **`StaticInventory` and Binding Push (ADR-0021, `crates/app_orchestration/src/resolver/registry.rs`, `crates/app_supervisor/src/service/reconcile.rs`).** In `[LFC-MGT]` (L1139), explicit bindings are described as pre-resolved by the orchestrator before config injection. The spec omits the built ADR-0021 mechanism: the App Supervisor continuously pushes bindings directly into constituent service configuration at deploy and scaling time, populating `StaticInventory` and completely bypassing runtime directory lookups on the RPC hot path.
2. **Stable Member Master DID vs App Instance Master DID (ADR-0020, ADR-0022, `crates/identity/src/keys.rs`, M05A Slice A7).** In `[LFC-MGT]`, the spec mentions services but omits the two-tier identity architecture: each member of a logical service maintains a stable member master DID (`SCOPE_SERVICE_INSTANCE` delegation), while the app instance carries an app-instance master DID minted at `adopt` and preserved across supervisor handovers (`export-master`/`import-master`).
3. **Preflight Verification and Bounded Remediation (`crates/app_supervisor/src/service/remediation.rs`, `reconcile.rs`).** The App Supervisor operational mode (L1143) mentions health monitoring, but omits the built bounded remediation engine: when health checks fail, the supervisor executes bounded restarts with exponential backoff up to `max_retries` before transitioning the service to an alerted state, preventing thrashing loops.
4. **Dual-Build Architecture for SynApps (M06B Slice B3, M06C Slice C1, traceability matrix row 55).** Developer tooling (`[ADV-DEV]`, L1182–1183) describes only WASM components, omitting the dual-build architecture where SynApps compile both to `wasm32-wasip2` and link natively via `syneroym-app-host-native` with parity suites proving identical behavior (`crates/app_host_native/tests/dual_build_parity`).
5. **Signed Record Envelope and Delegation Certificates (`crates/roym_core/src/record.rs`, `crates/signed_record/`).** Phase 6 describes portable data and quote/invoice cards, but omits the foundational wire format: every message, listing, card, credential, and receipt is wrapped in a versioned `SignedRecord` envelope carrying a delegation certificate that binds ephemeral device keys to the person's master DID.
6. **Recipient-Controlled First-Contact Rate Limiting and Deletion Records (`crates/roym_core/src/safety.rs`, `crates/conversation/`).** Phase 6 mentions messaging and spam prevention, but omits the built anti-spam mechanisms: recipients enforce sliding-window contact rate limits on unintroduced senders, and message deletion creates durable deletion records rather than silent removal.
7. **Supervisor Outbox, Dead-Letter Queue, and Replay Surface (`crates/app_supervisor/src/service/outbox.rs`, `apps/roymctl/src/commands/supervisor.rs`).** Application lifecycle management mentions pushing bindings, but omits the durable outbox and dead-letter queue mechanism that ensures binding updates reach offline or intermittent nodes, accompanied by an administrative inspection and replay CLI surface (`roymctl supervisor replay`).
8. **Static Asset Blob Pass-Through without Component Instantiation (M06A, `crates/control_plane/src/service/orchestration/backends.rs:170`, `static_assets_e2e.rs`).** SynApp lifecycle management omits the static asset pipeline: SynApps can package asset bundles (`--assets`) stored directly in blob storage, allowing the client gateway to serve web UI files without waking or instantiating the WASM runtime.
