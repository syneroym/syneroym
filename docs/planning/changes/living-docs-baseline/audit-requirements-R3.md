### Main findings

1. **Trust and agreement primitives are solidly implemented, but web-of-trust and public reviews are Envisioned.** The codebase implements cryptographic identity continuity (`crates/identity/src/delegation.rs`), signed membership credentials and revocations (`crates/roym_core/src/membership.rs`, `crates/roym_directory/src/app/credential_ops.rs`), and immutable interaction and fulfilment receipts (`crates/roym_core/src/transaction.rs:86-150`). Consumer referral vouches, web-of-trust decay formulas, and public consumer reviews are not built (Owner Decision Q-B3; Matrix row 14 `[PRD-TRU]` / `[P2P-REP]` is open for milestone M8).
2. **Third-party conformance testing and public capability governance do not exist yet.** The spec requires an executable conformance suite, public proposal process, and capability certification (lines 411–422). WIT interfaces are versioned packages (`crates/wit_interfaces/wit/`) and dual-build parity is tested (`crates/app_host_native/tests/dual_build_parity.rs`). However, an executable public conformance suite is not built (`[PRD-EXT]` is Pending in Matrix row 16), and dynamic protocol capability negotiation is deferred (Matrix row 48 `[LFC-VER]`).
3. **Formal pre-launch threat model documents and privacy data inventories are missing.** Line 385 requires a reviewed threat model and privacy data inventory covering key compromise, metadata leakage, and DoS before production use. While technical mitigations exist in code (WASM fuel metering, `mlock` KEK protection, Double Ratchet encryption, contact rate limits), no formal standalone threat model document or data inventory exists in the repository.
4. **Data export and tombstone deletion are built; comprehensive multi-party account deletion is not.** Export is fully implemented using signed backup archives (`apps/roymctl/src/commands/roym/backup.rs`, `crates/roym_directory/src/app/backup.rs`). Deletion of chat messages replaces readable content with durable tombstones (`crates/conversation/src/host_impl.rs:333-338`). A comprehensive account deletion workflow coordinating erasure across providers, operators, backup stores, and peer nodes is not built.
5. **The legal liability section mentions Aggregators, which must align with project architecture.** Lines 498 and 500 mention Provider Aggregators. Under Owner Decision Q-A4 (`audit-architecture-overlaps.md` O22), an Aggregator is not an infrastructure hosting provider. It is a directory-type SynOrg service (`crates/roym_directory/src/app.rs`) that aggregates listings and credentials.

## 4. Gaps noticed

1. **Master Anchor DHT Revocation Deny List (`crates/core/src/dht_registry/master_anchor.rs`, `ADR-0020`).** The Trust Model (Layer 1 and Layer 3) discusses identity continuity and credential revocation, but omits the built substrate revocation mechanism: Master Anchor records published to the Mainline DHT / community registry storing a cryptographic deny list of revoked instance keys.
2. **Client Gateway Identity and Session Token Bridging (`ADR-0024`, `crates/client_gateway/src/session.rs`).** The onboarding section (lines 361–364) discusses lightweight consumer device identities, but omits the built Client Gateway mechanism: a local proxy on port 7960 issuing short-lived cookie/bearer session tokens that map browser keys to delegated Ed25519 DIDs without exposing private keys to app runtimes.
3. **Fine-grained Data Access Engine (FDAE) Policy Audit Traces (`ADR-0017`, `crates/fdae/src/trace.rs`).** The spec (lines 359–360, 376–378) requires that delegated administration is audit-recorded and access grants are scoped, but omits `DecisionTrace` provenance emitted by FDAE recording every evaluated rule, row filter, column mask, and subject DID.
4. **Substrate Claim Tool and `ControllerAgreement` (`crates/identity/src/substrate.rs:48`, `apps/roymctl/src/commands/substrate.rs:67-175`).** The onboarding section (lines 355–357) discusses choosing a self-hosted or managed-guild path, but omits the concrete mechanism: `roymctl substrate claim` creating an immutable cryptographic `ControllerAgreement` binding the substrate's host key to a controller owner DID with an expiry.
5. **Two-phase Signed Record Envelopes with Canonical JSON and Content Digests (`crates/signed_record/`, `crates/roym_core/src/record.rs`).** The trust model specifies verifiable credentials and interaction receipts, but omits the built envelope format: signed records with canonical integer-only JSON serialization, Ed25519 signatures, and SHA-256 content digests.
6. **Inbound Contact Admission and Recipient Rate Limits (`crates/roym_core/src/safety.rs:16-146`).** The safety section mentions reporting and abuse prevention, but omits the built mathematical admission filter: recipient-configurable sliding window contact limits (`ContactLimits`, `admit_first_contact`) that block unsolicited contact before message delivery.
7. **Directory Pruning and Retention Engine (`crates/roym_directory/src/app/publication_ops.rs:346-485`).** The data lifecycle section (lines 370–371) mandates documented retention policies, but omits the built active directory pruning loop that enforces `retention_secs` and automatically purges expired publications during search and sync passes.
8. **Durable Message Deletion with DAG Tombstones (`crates/conversation/src/host_impl.rs:333-338`).** The data lifecycle section (lines 379–381) requires that deletion identifies data held locally and does not promise what it cannot enforce, but omits the specific conversation tombstone mechanism that drops the readable body while retaining message ID and timestamp in the DAG.
