# Audit: architecture doc, batch C (Layer 4, Federation, Consumer Experience)

Reader: a developer who will split and fix [system-architecture.md](../../../system-architecture.md).

This audit covers these headings of the architecture doc:

- "Layer 4 — SynApp Specifications" (SynApp 1: Component Architecture, Order State Machine, Consumer Transaction Flow, Recommendation Algorithm)
- "Federation Architecture" (Cross-Substrate Discovery Flow, Minimum Federation Contract)
- "Consumer Experience Architecture" (Consumer App Architecture)

It changes no code and does not edit the doc. Part of the [living docs baseline](change.md). All checks are static reading. I did not run the substrate or the tests.

**Verdicts.** Only code and tests count as proof. Paths are from the repository root. The doc's status model has two values: no marker means implemented, "Envisioned" means wanted and not built. Verdicts describe what the audit found. They are not doc status values.

- **MATCHES**: the code does this.
- **DIVERGES**: the code does something different. The code is right, so the doc needs a fix.
- **NOT BUILT**: nothing in the code does this. "Presented as" says whether the doc writes it as working or as planned.
- **STALE**: a name was renamed or removed. The current name is given.
- **UNCLEAR**: I could not decide.

**Context for the whole batch.** The doc calls this "SynApp 1" and describes provider "Spaces" with seven WASM components. The code has no such components. The real product is Roym, one SynApp of six services: `web`, `profile`, `conversation`, `catalog`, `transaction`, `directory` (`crates/roym_core/src/services.rs:11-23`, `crates/roym_core/app/roym.toml`). "Provider Space" is a retired name ([TERMINOLOGY.md](../../../TERMINOLOGY.md), "Say / don't say" table). The Roym flow is also different from the doc's flow. Each person runs their own substrate with Roym. The consumer's UI talks to the consumer's own node. The two nodes exchange signed records as cards over the `conversation` service. No service on the provider's node is called directly by the consumer (`crates/roym_core/src/admit.rs:19-30`, `crates/roym_transaction/src/app.rs:221`, `crates/roym_catalog/src/app.rs:88`).

Main findings:

1. **Almost all of Layer 4 is written as working, and most of it is not the real design.** The seven WASM components (`space-manager`, `order-engine` and the rest) do not exist. Four of them map to real services under other names. Three have no code at all (`payment-adapter`, `notification-dispatcher`, `review-engine`), plus the DRM OCI service.
2. **The order state machine is not the code's state machine.** There is no order entity. The code has a chain of signed records (request, quote, agreement receipt) and then a booking with six states: `scheduled`, `in-progress`, `completed`, `cancelled`, `conflict`, `ended-unconfirmed` (`crates/roym_core/src/booking.rs:40-47`). Payment and fulfilment are two separate tracks, not states. Dispute, refund and review states have no code. The conflict rules assume a consumer cancel, which does not exist. The doc contradicts itself: "Storage & Write Arbitration" already says "Roym has no order entity" and marks the order rule Envisioned.
3. **The transaction flow and the Stripe payment flow are not built.** Payment is out-of-band by design. The provider signs a `payment-request`. The consumer pays outside Roym. Either side signs a `payment-acknowledgement`. Roym states it "does not see the money move" (`crates/roym_core/src/booking.rs:26-27`). The doc's own "Payments" section already says this. The sequence diagram contradicts it.
4. **The federation diagram shows shard lookup, which is not built.** Search is a client fan-out over a list of directories the person added (at most 8). Each directory is a Roym `directory` service run by a SynOrg (a local group's owner). Results are verified on the consumer's node. No routing descriptor, rendezvous hashing, leaf shards or local index cache exist. This matches the "No distributed shard index" line in the Roym spec.
5. **Consumer App Architecture describes native shells that are not built.** The consumer app is a web UI (Vite and TypeScript) served by the `web` service from the person's own node. It holds a delegated temporary key only. Message encryption runs in the substrate (`vodozemac`), not in the client (`libsignal`). Option C (guest browse) does not exist: every method except `profile.policy` needs an owner session.
6. **The recommendation algorithm has no code.** No recommendation, scoring or collaborative-signal code exists in `crates/` or `apps/`.

## 4. Gaps noticed

Architecture-relevant behavior in the Roym code that this batch does not mention (at most 8):

1. **Cards.** Seven signed record types travel as cards over `conversation` with content type `application/vnd.roym.card+json` (`crates/roym_core/src/card.rs:9-30`). The doc has "Action Card Architecture" in Phase 6 but not the real card set.
2. **Local-only admission.** Every Roym service except `directory` refuses a non-local caller with `-32013`; `directory` admits four wire methods (`crates/roym_core/src/admit.rs:19-30`, `crates/roym_directory/src/app.rs:70-78`). This is the key boundary of the Roym trust model.
3. **Booking tracks.** Payment and fulfilment tracks with a 30-day window and an "against interest" rule (`crates/roym_core/src/booking.rs:18`, `:259-282`).
4. **Slot claiming.** First-claim seat fence against double booking, with named `conflict` reasons `slot-taken` and `slot-unavailable` (`crates/roym_transaction/src/app/ledger.rs:66-130`, `crates/roym_core/src/booking.rs:66-72`).
5. **SynOrg directory and membership credentials.** Credential issue, revoke, suspend, lift, and standing checks (`crates/roym_directory/src/app.rs:214-221`, `:231-232`). Not described in the Federation section.
6. **Single-writer booking progress.** Provider-signed `booking-progress` snapshots verified by the consumer against the quote's signer (`crates/roym_core/src/booking.rs:329`).
7. **Browser login by delegated key.** The Hub login (`delegated-key`, separate auth origin, ADR-0024) is the real identity path for the consumer app (`crates/roym_web/ui/src/session/login.ts:1-35`).
8. **Safety rules.** Block, report, per-sender contact limits and publication limits (`crates/roym_profile/src/app.rs:78-85`, `crates/roym_core/src/safety.rs`).
