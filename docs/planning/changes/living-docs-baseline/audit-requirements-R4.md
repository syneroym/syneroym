### Main findings

1. **The Conceptual Model contains multiple stale entity names and obsolete relationships.** The diagram entities `MOD` (`SYN-MOD`), `SPACE`, and `SPACE-MGR` do not exist in the codebase (Overlaps O24; Glossary entries GLS-08, GLS-13, GLS-14). Components are defined as WASM components or OCI images in `ServiceDefinition::source` (`crates/app_orchestration/src/models/service.rs:13-35`), and domain functionality is structured into catalogs, listings, and directories (`crates/roym_catalog`, `crates/roym_core/src/listing.rs`, `crates/roym_directory`).
2. **Aggregator hosting and vouching diverge from the system architecture.** The conceptual diagram asserts that an `AGGREGATOR` "manages-for" and "vouches-for" providers (lines 535, 555). In code and architecture decisions (Owner Decision Q-A4, `audit-architecture-overlaps.md` O22), an Aggregator is not an infrastructure hosting manager. It is a directory-type SynOrg service (`crates/roym_directory/src/app.rs`) that aggregates provider listings and credentials. Hosting is performed by substrate operators claimed via `ControllerAgreement` (`crates/identity/src/substrate.rs:48`).
3. **The centralized Bootstrap Server and dynamic relay assignment are Envisioned, not built.** Lines 589–590, 634, and 640–655 specify a Syneroym-operated Bootstrap Server that assigns home relays, maintains an official relay directory, verifies community relays, registers `*.syneroym.xyz` DNS records, and performs HTTP redirects. None of this exists in code (Owner Decision Q-A8; Overlaps O10). Substrates connect to a statically configured coordinator relay URL (`parent_coordinator.iroh.url` in `crates/core/src/config.rs:160-175`) and publish signed endpoint records to the Community Registry (`crates/community_registry`) or Mainline DHT via pkarr (`crates/core/src/dht_registry`).
4. **Consumer-facing aggregation and multi-directory search merge are solidly implemented.** The consumer experience across multiple independent substrates is unified by the Roym Hub web application (`crates/roym_web/ui/`). Multi-directory search query fan-out and deterministic round-robin client merging with visible source DID attribution and recency provenance are fully implemented (`crates/roym_directory/src/app/client_merge.rs`, `client_query.rs`) and verified by end-to-end tests (`crates/substrate/tests/roym_directory_e2e.rs`, `crates/substrate/tests/e2e/roym-hub.spec.ts`).
5. **Core Substrate primitives and SynApp lifecycle management are operational.** The substrate provides embedded MQTT messaging (`crates/mqtt_broker`), sandboxed WASM and Podman execution (`crates/sandbox_wasm`, `crates/sandbox_podman`), per-service encrypted SQLite data layers (`crates/data_db`), dual-build native linking (`crates/app_host_native/tests/dual_build_parity.rs`), Universal Proxy JSON-RPC translation (`crates/router/src/proxy.rs`), UCAN deploy capability authorization (`crates/control_plane/src/service/orchestration.rs`), and an active App Supervisor reconcile loop with MQTT alert publication (`crates/app_supervisor/src/service.rs`). Advanced lifecycle features such as automated package signature verification, dynamic GPU/disk quotas, and mobile OS background push notifications are Envisioned.

## 4. Gaps noticed

1. **ControllerAgreement Cryptographic Ownership Protocol (`crates/identity/src/substrate.rs:48`, `apps/roymctl/src/commands/substrate.rs:65-115`, `ADR-0020`).** Substrate Setup (lines 585–588) states that the substrate creates an administrator credential on first run, but omits the built protocol: `roymctl substrate claim` creating an immutable cryptographic `ControllerAgreement` mutually signed by the node's DID and the controller's master DID, without which the substrate fails closed and grants `substrate/admin` to nobody.
2. **Dual-Build Native and WASM Component Execution (`ADR-0021`, `crates/app_host_native/tests/dual_build_parity.rs`, `crates/control_plane/src/synsvc_native.rs`).** SynApp Lifecycle Development (lines 675–678) mentions WebAssembly and container images, but omits the major dual-build architecture: the same SynApp source code compiles both to a `wasm32-wasip2` sandboxed component and linked natively into the substrate host binary, proven identical in behavior by comprehensive parity test suites.
3. **App Supervisor Resident Reconcile Loop & Desired State Engine (`ADR-0021`, `crates/app_supervisor/src/`).** Substrate Functionality and SynApp Deployment/Monitoring mention monitoring and restarting services, but omit the core built supervisory mechanism: the resident App Supervisor managing multi-substrate placement, inventory tracking, unattended certificate renewals, desired state reconciliation (`SupervisorService::run`), and MQTT alert publication (`crates/app_supervisor/src/service.rs:654-680`).
4. **Fine-grained Data Access Engine (FDAE) Compiled ReBAC Policy Pushdown (`ADR-0017`, `crates/fdae/`).** Access Control (lines 622–627) and SynApp Deployment (lines 681–684) describe access policies and declarations, but omit the concrete built mechanism: declarative Relationship-Based Access Control (ReBAC) policies compiled into SQLite `WHERE EXISTS` / recursive CTE pushdown sieves that prune rows and mask columns before data reaches application logic.
5. **Client Gateway Port 7960 Session Bridging & Cookie Auth (`ADR-0024`, `crates/client_gateway/src/`).** Consumer-Facing Aggregation (lines 656–669) describes consumer apps connecting to substrates as thin clients, but omits the built architectural bridge: the Client Gateway running on port 7960 that mediates browser HTTP/WebSocket requests, issues short-lived session tokens, and maps cookie-authenticated browser sessions to delegated Ed25519 person DIDs.
6. **Client-Side Search Fan-out and Deterministic Round-Robin Merge (`crates/roym_directory/src/app/client_merge.rs`, `client_query.rs`).** Consumer-Facing Aggregation (line 662) states that the consumer app queries multiple directories and merges results, but omits the built mathematical merge engine: asynchronous fan-out across multiple directory DIDs, deduplication by listing ID, and deterministic round-robin interleaving capped by `MAX_SEARCH_RESULTS` and `MAX_REFUSED_RESULTS`.
7. **Master Anchor DHT Revocation Deny List (`crates/core/src/dht_registry/master_anchor.rs`, `ADR-0020`).** Core Substrate Identity (lines 617–620) mentions managing key storage, rotation, and revocation, but omits the built DHT mechanism: Master Anchor records published to the Mainline DHT via pkarr containing signed cryptographic deny lists of revoked instance and routing keys.
8. **Deployment Journal with Two-Phase Rollback (`crates/app_orchestration/src/journal.rs`, `reconcile.rs`).** Deployment Lifecycle (lines 689–690) states that partially failed deployments are rolled back without undeclared services, but omits the built transaction mechanism: an SQLite-backed deployment journal tracking sequential reconciliation actions (`ActionRecord`) that automatically rolls back partially registered services and database allocations on failure.
