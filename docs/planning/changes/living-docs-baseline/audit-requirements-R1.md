### Main findings

1. **The Glossary and entity models contain stale terms that do not match the codebase.** `SYN-MOD` is never used (code uses `ServiceDefinition::source` for WASM component or OCI image). `Space` and `Space Manager` are never used (code uses SynApp instance, catalog, and provider). `Home Relay` is described as dynamically assigned per-service, whereas the code configures a static coordinator relay URL at the substrate level. `Aggregator` is described as a hosting manager for providers, whereas the owner decision and code establish it as a directory-type SynOrg service (`crates/roym_directory`).
2. **The "Bootstrap Server" and "Vouching" are described as active features, but neither exists in code.** No bootstrap server assigns relays, tracks active services, or synchronizes with the DHT. Instead, the substrate uses a statically configured parent coordinator relay and publishes signed endpoint records to the community registry (`crates/community_registry`) and Mainline DHT via pkarr (`crates/core/src/dht_registry`). Vouching algorithms and web-of-trust scoring do not exist; trust is currently based on signed SynOrg membership credentials and revocations. Both must be marked `Envisioned`.
3. **Core requirement boundaries between the Substrate and the Roym product application are blurred.** The requirements overview and design principles describe agreements, receipts, trust signals, quotes, and payment records as shared substrate contracts. In reality, these are domain contracts of the Roym SynApp (`crates/roym_core`, `crates/roym_transaction`, `crates/roym_directory`), while the substrate provides general primitives (WASM/OCI sandboxes, SQLite data layer, blob storage, messaging broker, DID identity, and Universal Proxy).

## 4. Gaps noticed

1. **Client Gateway and Session Token authentication (`ADR-0024`).** The requirements overview describes a lightweight consumer identity, but does not specify the local HTTP client gateway proxy (port 7960) mapping host headers and authenticating sessions via cookies/bearer tokens into delegated DIDs (`crates/client_gateway/src/session.rs`, `gateway.rs:73`).
2. **Dual-build SynApp execution model.** The code supports dual compilation of SynApps: both as `wasm32-wasip2` components run inside Wasmtime, and linked natively into `syneroym-substrate` under the `roym` Cargo feature with identical behavior (`crates/app_host_native/tests/dual_build_parity.rs`, `crates/roym_core/app/roym.toml`). The requirements spec mentions only WASM and OCI container sandboxes.
3. **Fine-grained Data Access Engine (FDAE) and ReBAC pushdown.** The code implements declarative ReBAC compiled into SQLite `WHERE EXISTS` queries (row-level security and column-level masking) with a stage-4 WASM authorizer (`crates/fdae/`, `crates/data_db/src/sqlite/provider.rs`). The requirements overview only mentions general data sovereignty and access policy.
4. **Master Key vs Instance Key delegation structure (`ADR-0020`).** The code enforces a two-tier identity architecture distinguishing stable master DIDs (for nodes, app instances, and service members) from relocatable instance keys bound by signed `DelegationCertificate` carrying scopes like `SCOPE_ROUTING` and `SCOPE_SERVICE_INSTANCE` (`crates/identity/src/delegation.rs`). The requirements spec mentions DIDs generally but omits this dual-tier structure.
5. **In-process MQTT Broker for event pub/sub.** The substrate embeds `rumqttd` to provide pub/sub messaging over WIT `syneroym:messaging` alongside 1:1 and group conversation capabilities (`crates/mqtt_broker/src/lib.rs`). The requirements overview mentions messaging contracts generally but does not separate pub/sub event brokers from conversation channels.
6. **SQLCipher envelope encryption with KEK/DEK hierarchy.** The storage engine provides envelope encryption for SQLite databases using an `mlock`'d KEK in host memory and per-service encrypted DEKs in `substrate.db` (`crates/data_keystore/src/key_store.rs`). The requirements spec requires encryption at rest, but does not specify the KEK/DEK isolation model.
7. **Text route preamble wire protocol.** Inbound streams over Iroh QUIC and WebRTC negotiate routing via a text route preamble (`<scheme>://<interface>.<service_id>[?enc=...]`) with optional one-sided ECDH-P256 handshake (`crates/router/src/preamble.rs`, `handshake.rs`). This core dispatch protocol is not mentioned in the requirements overview.
8. **Directory search client-side merge and geographic area filtering.** Roym directory search performs geographic bounding box / radius filtering (`AreaFilter`) and client-side fanout merge across multiple independent directory services (`crates/roym_directory/src/app/client_merge.rs:30`, `search_ops.rs:136`). The requirements spec specifies local clustering, but does not describe client-side multi-directory merge.
